# yomiyasu — ブログ記事の文章作成

読者が前提や関係を自分で補わずに読み進め、必要な理解・判断ができる文章を作る。説明を組み立てた後に日本語を推敲する。短文化、文字数、技法の使用数、検査点数は目標にしない。

nanaism/yomiyasu（導入元コミット `602a3690dadd5d620bb21524353b8d192914eabb`）を基にした個人ブログ用の改訂版。元の著作権・ライセンスを保持する。

## 参照と優先関係

- 記事の新規作成・説明改善・構成検討では [blog-writing.md](references/blog-writing.md) を読む。
- 教材紹介・比較・選び方など、特徴の意味や適性を説明するときは [third-party-writing.md](references/third-party-writing.md) を読む。保存済みのお手本分析から、自然な第三者視点の説明を組み立てる。
- 出力前に [blog-review.md](references/blog-review.md) の「通常の文章確認」を使う。そこにある実装検証用の全ケースを、記事を書くたびに実行しない。
- 表現だけの小さな修正は本書と通常の文章確認で進め、説明技法が必要な場合に該当箇所を読む。
- この入口と上記2資料がブログ用の規則。既存の `references/domains/`、`gemini-syntax.md`、`slop-catalog.md` は導入元の詳細を調べる保守用資料として残す。通常のブログ執筆で自動読込せず、旧来の短見出し・数値目安・修正回数・汎用出力形式を再適用しない。
- 今回のユーザー指示を優先する。承認済みの記事は説明の丁寧さの見本であり、全記事の文字列・長さ・構成を固定するものではない。
- 同種の文章スキルを自動で重ねない。他スキルから呼ばれたときは、渡された読者・見出し・担当範囲・保持対象・出力形式を引き継ぐ。他スキルや設定を編集しない。

## 1. 依頼範囲を決める

依頼、会話、本文、資料から、読者／主な疑問／読後の理解・判断／前提知識／使用できる根拠／変更可能な範囲／出力形式を把握する。ユーザーへ定型フォームを要求せず、提供済みのことを聞き直さない。高校生本人、保護者、成人学習者などを一律に同じ読者へ固定しない。

| 依頼 | 進め方 |
| --- | --- |
| テーマと資料から記事を書いて | 必要な構成と本文を作る。仮レイアウトの承認待ちを勝手に挟まない |
| この構成で本文を書いて | 指定構成を保ち、配下の説明を組み立てる |
| 読みやすく・丁寧に改善して | 根拠のある説明補充、段落整理、表現の改善を行う |
| 構成から見直して | 見出しや節の順序も見直せる。過去の承認を永久の固定としない |
| 表現だけ・誤字だけ直して | 指定された範囲で意味・情報・構成を維持する |
| この節・段落だけ直して | 対象と確認できる前後だけを扱う。未読の全体を合格にしない |
| 仮レイアウトだけ | 見出し、各節が答える疑問、説明内容と順序を提示して止める |

「改善」の依頼で承認済み・指定済みの見出しがある場合は、それを基本に本文を整える。大幅な構成変更は構成見直しの依頼に従う。固定範囲では解消できない重要な矛盾は該当箇所だけ示し、必要な判断を求める。

記事本文の生成とファイル保存・公開の許可を混同しない。保存が依頼されたときも指定範囲だけを扱い、URL、frontmatter、引用、リンク先、画像、CTAや計測用属性などの保持対象を変えない。本文のみの出力と、元ファイルから画像等を削除することは別である。

## 2. 事実と説明の範囲を守る

推敲前後で、主張、比重、確実性、文の働き（事実・意見・提案・依頼・仮定・引用等）を保つ。主体、対象、時、数量と単位、否定、条件、例外、比較の軸、因果、順序も照合する。要約の依頼なら、残す主張に掛かる重要条件を保持する。

新規執筆と既存記事の説明改善では、次を区別して補う。

| 内容 | 扱い |
| --- | --- |
| 根拠にある定義・対応関係 | 読者に必要なら明示する。近くにある語というだけで指示語の対象を決めない |
| 確認済みルールから導ける計算や換算 | 条件・単位・丸めを確かめ、判断に必要な過程を示す |
| 説明用の仮定例 | 仮定と分かる形で使い、規則に沿わせる。実在の体験・口コミとして語らない |
| 筆者の提案 | 目的に必要で実行可能な範囲で提案する。効果保証や公式の義務へ変えない |
| 新しい仕様・料金・原因・効果 | 根拠を確認してから使う。未知のものを具体化という名目で作らない |

単なる表現修正では情報を増やさない。原文に誤りが見つかった場合は事実訂正と表現修正を区別し、依頼範囲に応じて訂正・報告する。未確認の主張に「かもしれません」を足すだけで根拠を得たことにしない。

現在の条件を案内する記事で、結論に必要な不足・矛盾・変動情報の古さがあるときは公式情報など適切な根拠を確認する。与えられた固定素材を使う文章比較では目的と確認時点を保つ。無関係な競合調査へ広げない。

軽微な不足なら分かる範囲で進める。主回答を左右する不足は調べられる範囲で解消し、なお必要な情報だけ確認する。未確定の内容を完成したように書かず、編集者向けの「要確認」や質問を読者向け本文へ埋め込まない。固定指示と事実が両立しなければ、許可された改善を進め、衝突箇所を未解決として示す。

## 3. 丁寧な説明を組み立てる

削る前に「これを削ると、読者は何を補う必要があるか」、足す前に「何を新しく理解・判断できるか」を確かめる。必要な説明は残し、同義の水増しはしない。

各節は一つの主な疑問を目安に、答え、意味・理由、区別、具体例、条件・例外、確認・行動から必要な要素を選ぶ。全要素やPREP等の固定順を毎節へ強制しない。料金・手続きの主回答を引き延ばさない。知識紹介や体験へ行動案を強制しない。

教材を評価する箇所では、確認済みの特徴が読者の使い方にどう関わり、何を理由に選べるかを本文へ織り込む。「筆者が評価したいのは」などの宣言を後付けしただけで第三者視点を満たしたとしない。すでに説明した利点を繰り返さず、目的により利点と注意点が変わるなら条件を示す。手順・定義・単独のFAQへ評価文を無理に追加しない。

- 一段落は一つの理解のまとまり。答えと理由、説明と短い例は同居できる。
- 前の文と次の文の関係を確かめ、理由・条件・対比・順序に合う言葉でつなぐ。滑らかにするための因果を作らない。
- 用語は正式名称を保ち、必要なら普通の言葉で意味を添える。定義しただけで操作も分かるとみなさない。
- 一つの例で説明を追えるなら、途中で別の場面へ切り替えない。例は根拠の代わりにしない。
- 表・一覧・本文は情報の関係で選ぶ。表の読み方が明らかなら説明を重ねない。
- 冒頭の答え、本文の説明、末尾の確認、途中から読む人への条件再掲は、それぞれの働きを確かめて残す。
- 文字数・段落数・箇条書き比率はノルマにしない。長さを見積もるときは「H2直下」「対象H3」「H3を含むH2全体」を明記し、二重計上しない。

## 4. 丁寧で自然な日本語へ整える

地の文は落ち着いた「です・ます」を基本にし、明示された文体指定があれば従う。「ですな」「でもって」「っす」などの特徴的な口調、煽り、皮肉、同意の強要、読者への決めつけは採らない。親しみは具体的な疑問と説明で出す。引用文・正式名称は地の文の口調変換から除く。

- 見出しは、話題や要点をつかめる形を選ぶ。「解約の締切は、最初に受け取らない月号から考える」のような説明型を自動で短い名詞句へ縮めない。「受付時間」等の項目型も用途に応じて使う。
- 見出し・表・要約だけでも重大な条件を誤解させない。本文末尾の注意で、入口の誤断定を解消したとみなさない。
- 主語と述語、修飾先、指示語を追えるか確認する。主体や対象が不明なら作らない。客観的な道具の動作は無理に人の行動へ変えない。
- 推量を断定へ、説明を義務へ、提案を保証へ変えない。「できます」「しましょう」「と言えるでしょう」で機械的に語尾を散らさない。
- 文長や読点の数だけで切り貼りせず、長い条件の掛かり先が分かるように整理する。短い断片や一文一段落を連続させてリズムを作らない。
- 「AではなくB」が混同を防ぐなら残す。重要度を担う語、必要な予告・要約も、定型表現に見えるという理由だけで消さない。
- 空疎な前置き、根拠のない比喩、名詞だけのコピー、不要な絵文字や装飾を整える。自然な慣用句や内容を区別する記号まで一律に消さない。
- 強調は理解を助ける箇所に絞る。Markdownの太字やリンクの書式を確認し、書式の修正で意味や範囲を変えない。

## 5. 出力前に確かめる

1. 読者の主質問と、取り違えを防ぐための問いを素材から定める。
2. 本文だけから答えと判断過程を取り出し、根拠と照合する。説明者の知識で穴を埋めない。
3. 用語・数字・条件、見出し・表との整合、前後のつながり、丁寧な口調を通読して確かめる。
4. 改善は原文と資料、新規は資料と照合する。部分入力は提供範囲だけを判定する。
5. 問題箇所・読者への影響・原因を説明できる問題を修正する。修正後に前後を読み、構成変更時は全文を確認する。具体的な未解決問題が残れば対応を続けるが、言い換えの往復や検査点数のための変更はしない。根拠・権限・固定条件の不足で解消できない点は完成扱いにしない。

全文の作成・改稿、ファイル保存、またはユーザーが検査を求めた場合は、利用可能なら既存スクリプトを補助に使う。軽微な部分修正では手動確認で足りる場合がある。コマンドと警告の扱いは [blog-review.md](references/blog-review.md) を参照する。検査を実行できない場合は同じ観点で確認し、実行済みと報告しない。

## 6. 依頼に合う形で返す

- 「本文のみ」なら、見出しや必要な出典を含む読者向け文章だけを返す。変更理由・採点・内部の技法IDを加えない。
- 「仮レイアウトのみ」なら、構成と説明内容を返す。全文執筆や保存へ進まない。
- 改善点や比較を求められた場合だけ、必要な理由と差を添える。通常の完成本文へ定型の長い検査報告を付けない。
- 根拠不足で答えを確定できない場合は、本文へ編集注記を混ぜず、必要な確認を短く行う。
- 使った規則や検査を問われたら、読んだ資料、実際の修正例、実行した検査と未実施の範囲を正確に答える。新しい常設ログや追加の出力欄は作らない。

## 7. 親記事スキルとの接続

親が `output_mode: parent_contract` を明示した場合だけ、以下の構造化結果を工程内で返す。通常の単独利用・「本文のみ」では6の出力を守り、検査欄を本文に印字しない。これは親による検収用であり、記事への掲載内容ではない。

入力は `mode: new | refine`、`input_format: markdown`、`review_scope: section | article`、対象の本文または新規執筆素材とする。節では `section_id`、`section_type`、`heading`、`heading_level`、`parent_heading`、`scope`、`connection`、`required_points`、`allowed_evidence`、`reader_profile`、`quality_profile.required/preferred/prohibited` を受け取る。改稿は原文も受け取る。`section_type` は `intro | heading | conclusion | faq` を用途に合わせて使う。見出しがない単位は見出し関連項目を省略できる。

改稿・検査する本文は`body`に受け取る。全文検査では`mode: refine`で全文の`body`と、予定する全単位の`section_id`・見出し・`required_answer_ids`を持つ`outline`も受け取る。導入・結論など見出しのない単位も識別し、本文と照合する。本文や予定範囲の不足を`article_complete: true`だけで補わない。

- `required_points` には回答ID、読者の疑問、回答、必要な説明順、解釈、条件・限界を文字列またはレコードで受け取り、解釈を事実へ変えない。`allowed_evidence` は対象主張・出典・確認日・適用範囲・確認状態を保持する。
- お手本分析を渡す場合の `writing_method` は方法資料だけを受け取る任意項目。確認した範囲・採用する説明方法・適用限界を使い、商品事実の根拠に数えない。未指定なら本スキルの保存済み分析を使える。
- 保持対象は `preserve_elements` に受け取れる。親から渡された実行ID・フィードバック文脈は保持し、親のログやルール集合を二重作成しない。承認済みルールは `quality_profile` へ対応づける。
- 対象が `/Users/yudaikato/Documents/AIフォルダ/ブログ/公開サイト・教材/勉強ブログ` の親実行なら、`$article-skill-feedback`の接続契約に従い、親が取得した`target_skill: yomiyasu`、`stage: writing`の有効ルールと文脈を使う。旧担当だけを対象にしたルールを名前の置換で取り込まない。この接続を別プロジェクトには適用しない。
- 根拠不足は親の調査工程、見出しの矛盾・不足は見出し工程へ必要な変更を返す。指定外の調査・見出し変更や、同種の別文章スキルの自動併用で埋めない。

```yaml
status: section_pass # section_pass | article_pass | needs_execution_input
review_scope: section
body: "検収対象のMarkdown本文"
checked_sections: [H2-01]
answer_checks:
  - answer_id: A-01
    body_location: "見出しIDと回答箇所を識別できる短い記述"
    evidence_refs: [] # 入力中の出典URLまたは根拠識別子。未確認の出典を作らない
    result: pass # pass | fail
preservation_check:
  result: pass # pass | fail | not_applicable
  details: "指定見出し・事実条件・リンク等の実際の照合結果"
unresolved_items: []
change_requests: [] # 必要時は原因工程・不足・影響箇所・必要な対応を記す
```

`quality_report: summary` では必要な確認結果だけを返し、本文外へ長い自己採点を付けない。適用される必須回答と保持条件を満たし、具体的な未解決問題がない節だけ `section_pass` とする。回答IDがない導入等は `answer_checks: []` とできるが、疑問への答えと担当範囲は確認する。

`article_pass` は `review_scope: article`、`article_complete: true` で、導入・全見出し配下・FAQ・結論など設計された全文と必要な根拠が提供され、実際に全文を確認した場合だけ返す。節の合格数や部分入力から推定しない。全文では `checked_sections` と必須回答の照合を全対象に広げる。満たせない場合は `needs_execution_input` と理由を返し、作成できた本文も未検収として扱う。合格フラグだけで読みやすさ・正確性を証明したことにしない。
