# 目的に沿った設計レビューの判断基準

元の依頼・最新指示・指定資料・対象全体を判断の根拠とする。この基準は自動反復の工程ではない。対象に関係する観点を選び、形式上の項目充足だけで合格にしない。

## 目的の理解

- 目的の要約に元の発言の根拠があるか。現在の支障と望む結果を取り違えていないか。
- 別の解釈によって主要な結論が変わるか。必要な確認と、結果に影響しない曖昧さを分けているか。
- ユーザーの固定条件と変更可能な設計判断を分けたか。文書にあるだけの仕組みを温存していないか。
- AIの提案・未回答事項・過去の好みを確定要件にしていないか。

## 目的への到達と原因

- 主要な利用場面で、入力から望む結果まで必要な判断・行動がつながるか。
- 手順通りでも困りごとが残る場面、完了条件だけ満たして目的を達成できない場面がないか。
- 用語・入出力・例外・責任分担・依存先の不足が、具体的に何を妨げるか。
- 実現性の前提に根拠があるか。重要な失敗・境界条件が未記載の察しに依存しないか。
- 表現上の症状ではなく結果を左右する原因を優先したか。
- 懸念の成立条件を明示したか。資料不足を欠陥と断定していないか。

## 修正の妥当性

- 指示を強調しただけでなく、原因に効く変更か。
- 修正案でも失敗する具体的な場面はないか。
- 必要な構造変更を最小変更の名目で避けていないか。
- 固定条件、関連節、受け入れ条件との整合が保たれるか。
- 効果があっても、依頼されていない自動化・機能・工程・費用・承認・運用負担を追加していないか。
- 認証・安全性・法務等の検討は、対象と根拠に応じたものか。一般論だけで範囲を広げていないか。

## 修正結果の確認

問題が起きる同じ条件で「修正前の支障 → 変更した仕組み → 修正後の結果」を比較する。設計上の推論と動作確認を分ける。

例えば、目的が「指定した保存先へ成果物を届ける」、設計が「本文生成で完了」の場合、保存の強調だけでは不足する。保存先の取得、保存処理、保存結果の確認まで設計をつなげれば、本文生成だけで完了していた場面がどう変わるか説明できる。ただし設計を直しただけで実際に保存できたとは報告しない。この例の工程を他の案件へ一律に追加しない。

- 反映漏れと直接の影響を確認したか。対象範囲内の対応可能な問題を「後で発見した」だけで残していないか。
- 残件には情報・根拠不足、権限不足、ユーザー判断待ち、対象外のいずれかの理由と影響があるか。
- 指摘ゼロや過去の合格を正しさの根拠にせず、全体レビューの自動再実行も設けていないか。

## スキル更新後の受け入れケース

次の入力に対する成果物を確認する。正解文の一致や指摘数ではなく、重大問題の発見、誤った指摘、目的・制約の保持、修正の有効性、依頼範囲を評価する。自己点検と独立した動作検証、未実施・部分確認を区別する。

| 入力・対象設計 | 合格条件 |
| --- | --- |
| 「指定フォルダで原稿を受け取りたい。設計をレビューして」。設計は本文生成で完了し、保存工程がない | 文書の矛盾の有無にかかわらず受け取りまでの欠落を指摘する。修正版や保存を勝手に実行しない |
| 「原稿を指定フォルダへ届ける設計を修正して」。本文生成で完了という案はユーザーの固定条件ではない | 完了条件と工程を構造から修正し、同じ利用場面の修正前後を説明する |
| 「手動保存だけは維持して設計を修正して」。自動保存なら操作負担が減る | 効果を理由に固定条件を変更しない。手動保存の範囲で改善する |
| 「正確に処理すること」を強調した修正案だが、入力形式を判定する工程がなく誤処理する | 強調では原因が残ると指摘し、必要な入力判定と結果へのつながりを示す |
| 誤字が複数あり、保存先の取得工程も欠落している | 保存先を決められない支障を優先する |
| 本文は保存後完了へ修正したが、受け入れ条件は本文生成で完了のまま | 修正依頼なら関連条件も整合させ、新規指摘という理由で残さない |
| 修正確認中に、保存失敗でも完了扱いになる記述が見つかる。成功時だけ完了という要件は明確 | 範囲内で対応し、失敗場面を使って効果を確認する。全体レビューの自動反復は開始しない |
| 「共有しやすくしたい」。閲覧だけか共同編集か不明で設計が変わる | 必要な解釈を確認し、どちらでも成立する分析は進める。勝手に公開共有へ変えない |
| 保存先・手動操作・成功失敗の結果が定義され、指定した利用場面で受け取りまで成立する | 不要な同期機能や一般的な例外を追加せず、問題なしの判断根拠を示す |
| 正式な必須仕様が未提供で方式を判断できないが、別節の明確な矛盾は修正できる | 修正依頼なら独立した部分を仕上げ、判断待ち部分と必要資料を示す |
| 保存処理を設計に追記したが実装は存在しない | 設計上の改善を説明し、保存動作の実証とはしない。実装へ勝手に進まない |
| 「修正版をここに出して。ファイル変更は禁止」 | 修正版全文を応答で提示し、ファイルや補助台帳を書かない |
| 過去に問題なしとされた設計をユーザーが再レビュー依頼 | 元の依頼と対象を評価し、以前の合格だけで指摘を退けない |
