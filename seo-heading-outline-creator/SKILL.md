# SEO記事見出し構成作成

## 目的と適用範囲

`seo-keyword-competitor-research` が完了して出力したリサーチレポートを入力に、検索意図・想定読者・競合との差分・根拠を反映した、記事のタイトル候補、H1、H2、H3を設計する。検索意図に答えるだけでなく、公式サイトの説明や短い分類名に寄らず、読者が続きを読みたくなり、判断・比較・実行へ進める構成であることを明示的な品質ゲートで検証する。タイトル文字数と、導入文・各H2・記事全体の予想文字数も出力する。

このスキルは、次の作業には使わない。

- 新しいGoogle検索、競合調査、キーワード選定、検索ボリューム調査
- 記事本文、メタディスクリプション、画像、内部リンク文、WordPress投稿の作成
- 入力にない事実・比較結果・最新性を必要とする主張の補完

新規調査が必要な場合は、`seo-keyword-competitor-research` を先に実行する。本文作成や投稿は、ユーザーが別途明示的に依頼したスキルまたは工程で扱う。

## 最初に読むファイル

作業の開始時に、次の順で必ず読む。

1. [入力契約](references/input-contract.md)
2. [現在有効なSEO方針](references/current-seo-policy.md)
3. [見出し品質ゲート](references/heading-quality-gate.md)

最終回答の直前に、[出力形式](references/output-format.md)を読み、必要な監査表・停止理由・判定を漏れなく出す。

## 実行手順

### 1. 入力を固定し、リサーチ完了性を再確認する

ユーザーから、`seo-keyword-competitor-research` のレポート本文、またはその全内容を読めるファイルを受け取る。次の情報を抽出して、入力メモに固定する。

- ユーザーが最初に提示した対象キーワード、検索条件、調査日
- `target_query`、`main_keyword`、`required_subkeywords`、`optional_related_terms`の区分
- `Quality Gate` の結果、信頼度、既知の不明点
- 検索意図（主・副・除外）、ペルソナ、読者の悩みと到達点
- 上位ページ、SERPの不足、一次情報、差分候補
- `記事方針の推奨` と、既存記事のURL・現行見出しなどの実装前提

見出し設計では、情報源を次の二つに分ける。

- `method_source`: このスキルの実行手順、品質ゲート、出力形式
- `content_source`: 現在の対象クエリ、現在の上流リサーチ、現在のタスクについてユーザーが明示した条件または上書き

`method_source`は論点の抽出方法を決めるために使い、記事で扱う具体的な論点を供給する情報源としては使わない。過去の実行結果、別タスクの指摘、スキル内の例示、一般的な確認項目一覧を、現在の記事内容の根拠として再利用しない。

上流スキルが「完了」と示していても、それをそのまま信じない。`input-contract.md` の再確認条件を満たせない場合、本文構成を作らず、`needs_research` または `needs_user_decision` を返す。レポート内の「見出し案」は参考候補であり、正解として転記してはならない。

ユーザーが最初に提示したキーワード表記を、後から短い別表記へ置き換えない。複数語または複数キーワードがある場合は、`input-contract.md`に従って主キーワードと必須サブキーワードを固定し、タイトル・見出しを作る前に被覆先を決める。区分が曖昧で検索意図が変わる場合は、推測せず`needs_user_decision`にする。

### 2. 方針と作成範囲を決める

上流の推奨を、そのまま見出し作成開始の許可にしない。推奨値ごとの必要情報を入力契約に照らして確認する。

- `新規作成`、または必要前提がそろった`意図を分けて新規作成`だけは、構成設計へ進める。
- `既存記事へ統合`、`既存記事をリライト`は、対象URL・記事ID・現行見出し・編集範囲のいずれかが欠ければ、変更案を作らず `needs_user_decision` にする。
- `別キーワードを検討`、`追加確認`は、構成を作らず停止する。ただしユーザーが明示的に上書きした場合のみ、上書き理由と残るリスクを記録して進める。

リサーチが古い、根拠が不十分、対象範囲が曖昧など、見出しだけでは解消できない問題も停止対象である。未確認事項を推測やもっともらしい言葉で埋めない。

主検索意図から、次の`outline_mode`を一つ選び、出力に記録する。複合意図では主意図をモードとし、副意図は必要な章へ反映する。

- `evaluation_decision`: 商品・サービスを利用するか判断する
- `comparison`: 複数の選択肢を比較する
- `how_to`: 操作方法や手順を説明する
- `factual_explainer`: 制度・用語・仕組みを説明する

メリット・弱点・向き不向き・独自の判断材料は、`evaluation_decision`と`comparison`で必須とする。`how_to`や`factual_explainer`へ無理に評価章を足さず、前提条件、例外、失敗しやすい点、確認方法を優先する。

### 3. 構成の骨格を設計する

見出しを作る前に、`content_source`だけから次を確定する。

- `target_outcome`: 読後に読者が判断、比較、実行または理解できる状態
- `primary_information_need`: 対象クエリに対して最初に答えるべき情報要求
- `required_answers`: `target_outcome`へ到達するために欠かせない回答要件
- 各`required_answer`の`current_input_basis`、`evidence_status`、`omission_impact`、`outline_placement`
- 各H2の`reader_question`と`reader_outcome`。前者はその章で答える検索者自身の疑問、後者は読後に可能になる理解・判断・実行である

ここでいう見出しの「興味」は、刺激的な語や煽りではなく、自分に関係する答え、判断材料または次の行動が見出しから分かる状態を指す。`reader_question`と`reader_outcome`は現在の`content_source`と`required_answers`から作り、根拠のない期待や効果を足さない。

`required_answers`の件数は固定しない。`content_source`まで根拠を追跡でき、かつ、主検索意図への直接回答、読者の到達状態を実質的に変える情報、または他の必須回答を正しく理解するための前提・条件のいずれかに該当するものだけを採用する。必要な根拠が不足している場合は、一般論や過去事例で補わず`needs_research`にする。

各H2は、少なくとも一つの`required_answer`、またはその理解に必要な前提・条件へ対応させる。対象クエリへの直接性、`target_outcome`への影響、後続内容を理解するための先行性から優先順位を決め、優先度の高い要件を論理的に置ける最も早いH2で扱う。H2の番号や配置数は固定しない。どの要件にも対応しないH2は、削除、統合または役割の再設計を行う。

`primary_information_need`への直接回答は、論理的に置ける最も早いH2、通常はH2-01へ置く。根拠や安全性のために不可欠な前提がある場合だけ後ろへ送れるが、その前提見出し自体にも主質問との関係と読む理由を示す。

検索者が最初に知りたい答えを早い位置に置き、その後に判断材料、具体的な進め方、注意点、次の行動を並べる。見出しには一つの役割だけを与え、重複、論理の飛躍、同じ結論の繰り返しを除く。

タイトルや見出しへ使う数字は、現在の`content_source`だけから抽出する。数字は、最終構成の項目数、実質的な順序を持つ手順、外部世界についての事実数値、元の必須キーワードに含まれる数値語に分け、別タスクの例や競合が使った件数を転用しない。割合、金額、期間などの事実数値は、構成を作る前に原資料、時点、単位、対象範囲、必要な分母と根拠強度を確認する。主質問への回答に不可欠なのに十分な根拠がなければ`needs_research`とし、不可欠でなければ数字候補から外して構成を続ける。

数字や目標件数を先に決めて`required_answers`を分割、統合または追加してはならない。構成を先に確定し、その後で相互に区別できる項目数と実質的な手順順序を抽出する。数字入りタイトル案は、必須語、文字数、正確性、検索意図、構成との一致、自然さをすべて満たし、非数字表現より理解しやすい場合だけ有効候補とする。詳しい分類、根拠強度、採否条件は`current-seo-policy.md`、最終整合は`heading-quality-gate.md`に従う。

- タイトル候補を3本作り、各文字数を示す。3候補すべてに`main_keyword`と全`required_subkeywords`を含める。一つの検索語として提示された場合は実質語の順序を保ち、複数キーワードとして提示された場合は自然な日本語になる順序で配置する。空白の削除や助詞の追加は認める。ユーザーが完全一致を指定した場合はそれを優先する。有効な数字入り案がある場合は少なくとも1候補で使い、必須語群に元から数値語がない場合は少なくとも1候補を非数字表現にして比較する。有効な数字案がなければ新造せず、不採用理由を記録する。
- タイトルは32文字前後、原則40文字以内とする。30〜34文字を推奨、28〜36文字を許容範囲とし、検索意図・差分・誇張回避・見出しとの一致から推奨案を一つ示す。キーワード自体が長く40文字以内に収められない場合、未承認の省略や超過をせず`needs_user_decision`にする。
- H1は、記事が解く中心課題と対象範囲を明らかにする。タイトルと完全一致にせず、意味を補完する。
- `main_keyword`は、`primary_information_need`へ直接答えるH2の少なくとも一つに自然に含め、その章で中心課題へ実際に答える。自然な配置ができない場合は勝手に省略せず、キーワード区分または表記について`needs_user_decision`を返す。
- 各`required_subkeyword`は、内容上もっとも関係するH1・H2・H3のいずれか一つ以上に含め、その見出し配下で実際に答える。全見出しへの反復は不要であり、語を置くだけで本文役割がない場合は被覆と認めない。
- H2は対応する`reader_question`と`reader_outcome`を持ち、「扱う内容」に加え、疑問・条件・対比・判断・影響のいずれかを示して読む理由が伝わる章にする。「料金」「使い方」「メリット」などの分類名だけ、または「〜を評価」「〜を解説」の機械的反復を認めない。
- 「確認する」「確かめる」「調べる」などの語を一律禁止しない。読者が行う具体的な確認や手順なら使えるが、執筆者の調査作業だけを示し、読者が得る答え・判断・行動を説明できない見出しは採用しない。
- H2は原則として記事タイトルより短くするが、最初から文字数を削らない。内容と読む理由を確定した後に冗長語だけを削り、意味や興味が失われる場合は章の役割・分割・タイトルとの関係から再設計する。
- 必要なH2だけにH3を付ける。H3には興味表現を強制せず、親H2の根拠、条件、具体例、手順、注意点のいずれかを具体化させる。H3も執筆者の確認作業だけを示さず、親H2の`reader_outcome`へどう寄与するかを説明できるものにする。
- 親見出しで項目数を示す場合は、明示した対象項目数と一致させる。順序番号は、並べ替えると理解または実行に影響するグループだけに使い、同一グループ内の表記を統一する。すべての見出しへ番号を付けない。
- 専門用語・抽象語・断定表現は、ペルソナが理解できる語に直すか、直後に説明が必要な箇所として記録する。
- 必須語を落とさず、不自然に詰め込まない。必須語以外は単語の一致より、質問に明確に答える語を優先する。
- 競合との差分は、レポートで根拠が確認できる場合だけ取り入れる。差分のためだけの章や、裏付けのない独自主張は作らない。
- `evaluation_decision`と`comparison`では、異なる意思決定に影響する、独立した判断材料を2つ以上設ける。同じ注意点の言い換えを複数に数えない。上流レポートに2つ分の根拠がなければ創作せず`needs_research`にする。
- 評価姿勢を表すためだけに「第三者」などの語をタイトルや見出しへ機械的に入れない。ただし、その語が指定キーワードに含まれる、またはユーザーが明示した場合は除く。

### 4. 二案比較と例外の記録を行う

内部では、同じ`content_source`、根拠境界、未確認事項、禁止表現を共有する「答え先出し案」と「行動先出し案」を少なくとも比較し、品質ゲートに通りやすい案を採用する。どちらも根拠を緩めてはならない。二案の一方が、未確認情報・既存記事情報不足・推奨外の作成を含む場合は採用候補にせず、その理由を記録する。比較そのものより、根拠に沿った採用判断を優先する。

### 5. 品質ゲートで検査し、原因単位で修正する

`heading-quality-gate.md` のG1〜G7、キーワード被覆ゲート、数字品質ゲートN1〜N4、タイトル3候補・全H2・全H3の個別判定、100点評価、ペルソナ読了テストを全て実施する。総合92点以上でも、各評価軸の下限、キーワード被覆、数字の正確性・構造整合、タイトル候補、H2、H3、必須ゲートのいずれか一つでも満たさなければ不合格である。点数で弱い見出しを相殺しない。

読者価値の初見評価では、`target_query`、主検索意図、ペルソナ、タイトル、H2、H3だけを先に読み、前回の問題台帳、採用理由、根拠説明を見て弱い見出しを補完しない。その後に完全な`content_source`で根拠・正確性を別に確認する。修正後も基準は直前版ではなく、`target_query`、`primary_information_need`、`target_outcome`、`reader_question`、`reader_outcome`、`required_answers`とする。

不合格の場合は、問題台帳に「症状・根本原因・修正・影響見出し・読者価値の回帰・再判定」を記録し、原因単位で構成を修正して再検査する。必須キーワードの欠落は、点数ではなく構成上の不合格として直す。正確性が上がっても、読者の疑問、読後の到達状態、具体性または次の行動が消えた場合は回帰として不合格にする。表面的な言い換えを繰り返してはならない。固定回数では打ち切らず、必須基準を満たすまで修正する。ただし、一度構成から再設計しても同じ根本原因が残り、追加の修正根拠がない場合は`iteration_limit_reached`として停止する。根拠不足は`needs_research`、編集判断不足は`needs_user_decision`を優先する。

### 6. 出力を監査可能な形で返す

出力形式に従い、最終見出しだけでなく、入力確認、`content_source`、`target_outcome`、`primary_information_need`、`required_answers`、各H2の`reader_question`と`reader_outcome`、キーワード区分と被覆表、数字候補監査、`outline_mode`、方針、根拠、タイトル文字数、導入文・各H2・記事全体の予想文字数、H2・H3個別ゲート、品質ゲート、採点、ペルソナテスト、実際の修正履歴を出す。各見出しには `H1-01`、`H2-01`、`H3-01-01` のような安定IDを付ける。根拠には、レポートの節名または一次情報URLを添える。構成修正後は数字候補を再抽出・再集計し、古い件数、順序、値、単位、条件が残っていないことを確認する。予想文字数はSEO順位条件ではなく、必要情報を過不足なく執筆するための目安として扱う。

合格できなかったときは、見出し構成を「完成」として出力しない。停止状態、欠けている情報、次に必要なリサーチまたはユーザー判断を明確にする。

## ユーザーによる上書き

ユーザーが上流の推奨外の方針、特定の見出し、既存記事の扱いを明示した場合は、上書きを尊重できる。ただし、上書きの対象・理由・残る品質リスクを出力に記録し、未確認の事実を確定情報に変えない。

## データと外部操作の境界

会話中の入力レポートは、この構成作成と品質判定だけに使う。ファイル保存、既存ファイルの更新、WordPress・XMind・スプレッドシート・外部サービスへの書込みは、ユーザーから保存先と操作内容を明示して承認された場合にだけ行う。通常は会話内に結果を返し、外部へ書き込まない。

検索結果の引用、レビュー、SNS投稿などのUGCは、根拠が確認できる範囲で要約し、個人情報や不必要な引用を出力しない。
