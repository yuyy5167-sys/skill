# 差別化・品質ゲート

## 親設計との連携

親が編集設計を担う実行では、`execution_mode`を明示する。省略時の`full`は従来の単独実行であり、この文書の設計・生成・検品規則をそのまま使う。

- `design_only`は親エージェントが第1〜5節を実行し、次の設計だけを返す。画像生成、編集、保存、`FINAL_ASSET_READY`判定をしてはならない。
- `render_from_plan`は子エージェントが親の確定設計を実現する方式である。記事からメッセージ、コピー、構図、画風を再設計しない。この方式の規則は、自律設計に関するこの文書中の規則より優先する。

```yaml
thumbnail_design:
  article_id: ""
  design_version: ""
  thumbnail_message: {}
  selected_concept: {}
  image_plan: # section 3の全項目。exact_copyを含む
    article_message: ""
    exact_copy: []
    textless_exception: null # section 6の明示ユーザー指示と適用asset_id
    target_grade: ""
    character_or_personless: ""
    character_sheet_paths: []
    visual_motif: ""
    composition: ""
    text_position: ""
    subject_position: ""
    primary_prop: ""
    background_structure: ""
    focus_position: ""
    style: ""
    crop_and_safe_margin: ""
    elements_to_exclude: []
  reference_manifest:
    - path: ""
      role: character_sheet | style_example | composition_guide | comparison_image
      confirmation_status: direct_image_reference | viewed_and_transcribed | reference_unavailable
  pre_generation_review: {}
```

`render_from_plan`で必須項目が欠ける、参照状態が不足する、または設計内で矛盾する場合は推測で生成せず、`handoff_status: needs_parent_input`と、該当設計・根拠・必要な判断を含む`change_request`を返す。制作サブは、親の確認済み記録だけに依存せず、プロンプト化の前に`reference_manifest`の必要なキャラクター正本、画風見本、構図見本、比較画像を実際に開いて確認する。これは親のメッセージ・コピー・構図を再導出する裁量ではない。参照を開けない、または記録と一致しない場合も`needs_parent_input`を返す。`thumbnail_design`、`generation_request`、`generation_approval`、`image_only_readback`、`used_design_version`は出力に保持する。

`composition_guide`は任意であり、構図、場面、動作、情報構造の発想補助だけに使う。画像生成へ直接渡さず、目視した特徴を記事固有の構図へ変換して`viewed_and_transcribed`と記録する。鉛筆ラフの画風、ラフ内人物の外見、セル番号、枠線、グリッド、仮文字を継承しない。人物同一性は`character_sheet`、完成画風は`style_example`、差別化は`comparison_image`を正本とし、役割間で代用しない。

既存の親設計に`composition_guide`や`reference_integrity`がなくても、それだけで拒否しない。制作側が登録表から期待SHA-256を取得して使用参照を確認し、結果へ`reference_integrity`を追加する。既存設計に正本未確定の中学生人物が含まれる場合だけは生成せず、`needs_parent_input`とする。構図見本がないことを理由に確定済み構図を再設計しない。

親承認待ちでは資産の`status`と出力パスを`null`にする。設計だけを返す場合は`handoff_status: design_ready`、最終プロンプトを返す場合は`handoff_status: prompt_ready`を使う。生成後の資産状態と混同しない。

`render_from_plan`は、`thumbnail_design.design_version`、`used_design_version`、`generation_request.design_version`が一致し、`pre_generation_review.result: pass`の場合だけ、最終プロンプトを`generation_request: {request_id, design_version, final_prompt}`として先に返す。承認未到着時は`handoff_status: prompt_ready`、`status: null`、`generation_approval: null`を維持する。親から`generation_approval: {request_id, design_version, final_prompt, result: pass}`が戻り、3項目が完全一致し、未消費の場合だけ生成する。不一致または不合格は`handoff_status: needs_parent_input`、`status: null`、`generation_approval: null`とし、`change_request`へ不一致項目を残す。設計版またはプロンプト変更後の承認は履歴だけとし、承認を消費して生成を開始した時点でも`generation_approval_history`へ移してactiveな`generation_approval`を`null`に戻す。同じ`request_id`は一度だけ消費する。結果不明時は自動再実行しない。初回生成、再生成、画像編集のすべてでこの照合を繰り返す。権限、保存、生成後の品質ゲートはこの承認によって緩和されない。

## 1. 記事タイプから視覚モチーフを決める

| 記事タイプ | 有力な視覚モチーフ |
| --- | --- |
| おすすめ・比較 | 選択肢、比較カード、分岐、順位、選ぶ動作 |
| 口コミ・評判 | 意見カード、良い点と気になる点、賛否の対比 |
| 料金 | 電卓、料金表、カレンダー、費用内訳 |
| 使い方・手順 | 番号、矢印、工程、段階の変化 |
| トラブル・注意 | 原因と解決、警告、困りごとから安心への変化 |
| 勉強法 | ノート、問題、理解、行動、学習手順 |
| 体験・効果 | ビフォー・アフター、達成、変化 |
| キャンペーン | 条件、期限、チェック項目。確認済みの変動情報だけ |

この表は非排他的な発想支援であり、記事タイプごとの使用制限ではない。別タイプのモチーフも、`thumbnail_message` との対応理由を説明できれば使える。タイプに合うという理由だけで採用せず、記事固有の意味を最短で補強できるかを確認する。

記事タイトルの文字だけは視覚モチーフにならない。記事に合う場面内の教材や動作でもモチーフを満たせる。学習場面は人物・教材・机を一つの場面にまとめ、別枠アイコンや工程図を必須にしない。別図を追加する場合は、その図が補う未伝達の意味を説明する。図解は一律禁止せず、教材・費用なら物中心、選択肢なら比較、手順が主題なら工程図を検討する。実在サービスのロゴ、画面、星評価、口コミ文は根拠と許可なしに作らない。

## 2. 構図候補

- 文字左・視覚要素右
- 視覚要素左・文字右
- 中央見出し・周囲に視覚要素
- 上下分割
- 対角線または斜めの情報フロー
- ビフォー・アフター
- ロードマップまたは段階図
- カード比較
- 物中心の人物なし
- 人物の寄りと小さな図解
- 大きな主役モチーフと補助的な小人物

候補は機械的なローテーションで選ばない。記事の読者課題と最重要メッセージを最短で伝え、比較対象との重複が少ないものを選ぶ。

### 表現角度と情報構造

構図より先に、記事をどの意味から見せるかを `narrative_angle`、その意味をどの関係で配置するかを `information_structure` として分ける。

- `narrative_angle`: `change`、`choice`、`problem_solution`、`process`、`outcome`、`caution`、`experience` など
- `information_structure`: `contrast`、`sequence`、`hierarchy`、`breakdown`、`focal_scene`、`data_emphasis` など

記事に合う複数の方向があれば意味の異なる候補を検討する。ユーザー指定の比較案数を優先し、通常時は案数を埋めるために不要な案を作らない。これは軽量な設計案であり、生成枚数ではない。記事から候補を作った後に承認見本を目視して画風を合わせ、見本の配置・動作への無批判な転用を再確認する。

別案は `narrative_angle` または `information_structure` の少なくとも一方に意味上の違いを持たせる。色、左右配置、数字、装飾だけを変えた案は別案に数えない。

## 3. 生成前の完成予定図

画像生成や画像編集より先に、記事の中心メッセージ、固定文字列、対象学年、人物の有無と正本、視覚モチーフ、構図、文字位置、主役位置、主役小物、背景構造、焦点位置、画風、安全余白、除外要素を具体化する。

- 記事本文や設計書がある場合はタイトルより優先する。
- タイトルしかない場合は、明示されている学年、教材・サービス、記事タイプ、中心テーマだけを使う。評価、結論、料金、順位、口コミ内容を補わない。
- 人物、文字、小物を詰め込みすぎず、一目で伝える中心を1つにする。
- 16:9の全体だけでなく、`object-fit: cover` を使う小さいカード表示を想定して焦点位置と安全余白を決める。
- 画風は [スタイル文法](style-grammar.md) の標準画風を使う。ユーザーが別画風を明示した場合はその指示を優先する。

記事本文、記事設計、確認済み事実から、ユーザー指定コピーとは独立して次を導出する。

```yaml
thumbnail_message:
  context: "" # 文字として省略可能。ただし画像単体で対象テーマを識別できること
  reader_focus: ""
  core_takeaway:
    kind: answer | change | choice | action | warning | outcome
    text: ""
  supporting_facts: [] # 確認済みの補足だけ。なくても中核メッセージが成立すればよい
  one_glance_meaning: ""
  forbidden_implications: []
```

`core_takeaway` は必須だが、断定的な結論に限定しない。比較なら選択、手順なら行動、注意記事なら警告、体験記事なら到達点を使える。主質問と読む価値を示す形でも成立し、結論や全条件を画像内で説明する必要はない。既存の `kind` は読む価値の種類として選び、`text` に記事が扱う問いや到達点を明記する。`body_only_details` に本文へ任せる説明を保持する。条件省略で誤解を招く主張は条件を残すかコピーを変更する。ユーザー指定 `thumbnail_copy` はこの意味、事実、権利との整合を検査する対象とし、整合する場合は指定文字列を優先する。矛盾する場合は入力固定または根拠確認へ戻し、無断で意味を変更しない。

候補と採用案を次で記録する。

```yaml
concept_directions:
  - narrative_angle: ""
    information_structure: ""
    visual_logic: ""
    article_specific_reason: ""
    gates:
      message_fit: pending
      factual_and_rights_safety: pending
      small_card_robustness: pending
      visual_translatability: pending
      differentiation: pending
      generation_feasibility: pending
selected_concept:
  narrative_angle: ""
  information_structure: ""
  dominant_motif: ""
  reading_order: []
  reason: ""
visual_roles:
  subject_motif: ""
  conclusion_motif: null
  evidence_motif: null
  decoration: null
```

## 4. 生成前設計レビュー

完成予定図を作ったあと、画像生成や画像編集を呼ぶ前に全体をレビューする。

次の6項目を上位ゲートとしてすべて合格させる。平均点で相殺しない。既存の詳細検査を置き換えず、次の対応で包含して確認する。

| 上位ゲート | 維持する詳細検査 |
| --- | --- |
| メッセージ適合 | 記事との一致、文字、`thumbnail_message` と固定文字列の整合 |
| 事実・権利の安全性 | 未確認情報、ロゴ、権利、固定文字列 |
| 小型カード耐性 | 構図、安全余白、焦点位置、文字密度 |
| 視覚化可能性 | モチーフ、文字、小物を無理なく生成できるか |
| 差別化 | 視覚面と意味面の二層フィンガープリント |
| 生成可能性 | キャラクター同一性、画風、参照整合性、要求同士の矛盾 |

候補が複数ある場合は、全ゲートに合格した案の中から、独自性より記事との一致、明快さ、小型カードでの意味保持を優先して採用する。

### 記事との一致

- 記事のテーマを一目で理解でき、読者に誤解を与えない
- タイトルや本文から読み取れない結論、評価、数値を創作していない
- 見出しと視覚モチーフが対応している

### 文字

- 第6節の文字契約を満たし、確定文字列が最終プロンプトと一致している。空の `exact_copy` を形式だけで合格にしない
- 文字ブロックは3個以内で、最も強い見出しは1つ
- 小さいカードでも読める長さで、同じ語句を重複していない
- 顔、服、主役小物へ文字が重ならない。文字・顔・意味を担う小物は各辺8%を安全余白の目安とし、机・背景は端まで広げられる
- 未確認の料金、評価、順位、日付、キャンペーンを含めていない

### キャラクター

- 対象学年とキャラクターシートが一致し、髪型、服装、年齢感、配色を固定できる
- 人物の必要性があり、人物なし案よりも記事内容を伝えやすい
- 人物数、ポーズ、小物が複雑すぎない

### 構図と差別化

- 文字、人物、主役小物の優先順位と情報の流れが明確
- 小さいカードの切り抜きでも主役と中心文字が残る
- 6項目フィンガープリントの不採用条件に当たらない
- 色や左右反転だけで別案にしておらず、記事固有のモチーフがある

### 画風と生成可能性

- 線画とフラット色面が主体で、水彩は背景紙と色面内部だけに限定される
- 日本語文字と主輪郭線をシャープに保つ指示がある
- 全面水彩、写真、3D、強いアニメ塗りへ流れる曖昧な表現がない
- 人物、文字、小物の要求が過多でなく、指示同士が矛盾していない
- 固定する要素と生成モデルに任せる要素が区別されている
- 使用参照のパス、可読性、役割、状態、実測SHA-256を確認し、期待値との不一致を未確認のまま使用していない
- キャラクター正本が一意であり、構図見本や画風見本の人物で上書きしていない

### 参照整合性

期待SHA-256は、キャラクター正本については`character-sheets.md`、画風見本と構図見本については`style-grammar.md`の登録表を使う。使用する参照だけを検査し、変更を検出しても期待値を自動更新しない。

```yaml
reference_integrity:
  result: match | changed | unavailable | not_checked
  checked_at: ""
  changes:
    - path: ""
      role: character_sheet | style_example | composition_guide | comparison_image
      expected_sha256: ""
      observed_sha256: ""
      visual_role_consistent: true | false | null
      action: continue | needs_parent_input | blocked
```

- 同じ役割で、人物同一性または画風・構図の用途も維持されている差し替えは`changed`として記録する。変更後の画像を確認できる範囲では続行できるが、期待値は別の承認済みスキル更新まで変更しない。
- キャラクターの顔、髪型、服装など同一性が変わった場合は`blocked`とし、生成しない。
- 登録された役割自体が変わった場合は`needs_parent_input`とする。
- ファイルを開けない場合は`unavailable`とし、代用せず既存の停止条件に従う。
- 使用しない参照は`not_checked`でよい。特定の画像ライブラリだけがWebP等を読めない場合は破損と断定せず、実際に開ける別手段で確認する。
- `style_reference_changed`は`style_example`の変更だけを表す。キャラクター正本と構図見本の変更は`reference_integrity`だけへ記録する。

記事の意味、正確性、可読性、人物同一性、画風、差別化に影響する問題が残る場合は `revise` とし、画像を生成しない。発見した問題を修正し、影響箇所と完成予定図への影響を再確認して、必要な品質条件を満たしたら `pass` とする。レビュー全体を自動反復する仕組みにはしない。

好みの範囲で品質に影響しない観察事項は、修正回数を増やすためだけに変更しない。必要資料がない、判断できない、または修正しても改善しない場合は `BLOCKED` とする。

```yaml
pre_generation_review:
  result: pass | revise | blocked
  problems_found: []
  corrections_applied: []
  unresolved_problems: []
```

## 5. 二層フィンガープリント

### 第一層: 視覚面の6項目

各既存画像と新案を次で比較する。

1. 主役人物または人物なし
2. 主役の左右位置
3. ポーズ・表情・動作
4. 主役小物
5. 文字配置
6. 背景構造

画風、キャラクター同一性、文字の系統、配色の一部は共通してよい。上記6項目は観察の枠組みとして維持し、人物の同一性や一致数だけでは不合格にしない。

各比較対象について、構図、場面・動作、主役モチーフ、文字配置の共通点と、文言・色を除いた目立つ違いを記録する。次の場合は再設計する。

- 主役・動作・小物・配置がほぼ同じで、文言と色以外に目立つ違いを説明できない。
- 同じモチーフと文字配置が続き、小型表示で別記事として識別しにくい。
- 見本の記事固有の場面を、今回の記事との関係なく転用している。

左右配置だけの共通性は許容する。左右反転や色変更だけでは、意味のある差別化の説明にならない。同じ人物を再使用する場合も、位置・動作・小物をすべて変える義務はない。比較結果は対象パス、共通点、文言・色以外の相違点、判定理由として `visual_comparisons` に保持する。

### 第二層: 意味面の4項目

親手順「比較対象を選ぶ」で確定した、第一層と同じ比較対象について次を比較する。

1. `narrative_angle`
2. `information_structure`
3. `dominant_motif`
4. `reading_order`

`narrative_angle`、`information_structure`、`dominant_motif`が同じで、記事固有の意味上の差を説明できない案は不採用とする。第一層または第二層のどちらか一方でも不採用条件に該当すれば不採用である。

主色、カード数、カメラ距離、図形、情報フローも補助記録する。ただし、これらの1項目が同じという理由だけでは不採用にしない。

表現角度が実質1つしかなく、唯一の案が第二層で不採用になる場合は、`narrative_angle`を無理に変えず、`information_structure`、`dominant_motif`、第一層の構図・位置・背景構造を変える構造的な再設計を少なくとも1回試す。その後も改善がなく、新しい判断材料もない場合だけ `BLOCKED` とする。

## 6. 文字

- 通常は画像内の文字を必須とする。サムネイルは記事の主題が伝わる短いタイトル、H2画像はその節の短い要点を入れる。ユーザー指定の文言がなければ記事から設計し、サムネイルは `image_plan.exact_copy`、H2は `section_image_plan.exact_copy` を確定文字列の正本にする。
- `exact_copy: []` は未確定の計画では使えるが、そのまま生成前レビューを `pass`、設計を `ready`、画像を完成状態にしない。文字なしを明示したユーザー指示がある場合だけ、同じ計画内に `textless_exception: {user_instruction, asset_scope}` を保持する。`user_instruction` は指示原文、`asset_scope` は適用する実際の `asset_id` の配列（サムネイルは `thumbnail`）とし、現在の資産が対象であることを確認する。親の解釈、古い空配列、意味が絵だけで通じるという自己評価は例外の根拠にならない。
- 有効な例外では文字を入れず、文字関連の検査を `not_applicable` として原文・対象範囲を理由に残す。例外は文字の有無だけに適用し、意味・画風・実表示の検査は維持する。旧設計で空配列の理由がない場合は未確定扱いとし、`full` では文字を設計、`render_from_plan` では `needs_parent_input` を返す。
- 「文字量を減らす」「文字枠を減らす」では要点を保って短縮し、全文字を削除しない。サイトで後からタイトルを重ねるという未確認の前提で `Text: none` を出さず、サイト側の見出しや重ね文字を画像内のタイトルの代わりに数えない。
- 文字ブロックは3個以内、最も強い見出しは1個。3個は上限であり、埋める義務ではない。補足は誤解防止または読む価値の具体化に必要な場合だけ使う。
- 数字の強調は原則1か所。同じ語句を複数ブロックで繰り返さない。
- `primary`、`secondary`、`supporting` は意味上の役割であり、別々の文字ブロックを強制しない。
- 最初に読む要素を1つに定め、次に対象や文脈、最後に必要な補足が伝わる順を設計する。文字サイズの固定比率ではなく、小型表示でもこの順が維持されるかで判定する。
- 中心語だけを孤立させず、画像単体で対象テーマと最重要メッセージを一続きの意味として理解できるようにする。
- 記事タイトル全文を画像へ詰め込まず、記事固有の判断軸または読者利益を短くする。
- 料金、日付、順位、評価、キャンペーンは現在確認できた正確な情報だけを使う。
- 生成前に文字列を固定して最終プロンプトへ同じ文字列を渡し、生成後は実画像の文字の存在と1文字ずつの完全一致を確認する。各文字の観測箇所・一致・可読性を既存の `visual_review` またはH2の `checks` に保持する。形式・寸法の機械検査だけでは文字の合格を出さない。
- 承認見本の自然な丸みと読みやすさを基準とし、主見出しと補足の強さを分け、複数行をすべて最大サイズ・極太にしない。文字の太さ・色は絵の線・色と釣り合わせる。白縁・背景帯は必要性と画風への適合から選ぶ。
- 顔、制服・服、主役小物へ文字を重ねない。文字・顔・意味を担う小物には各辺8%を余白の目安とし、机・背景は端まで広げられる。端に近い要素の位置・改行・サイズを調整し、全体の一律縮小を既定にしない。実カードの切り抜きを最終確認する。

## 7. 生成と修正のゲート

- 初回から一律に二段階生成しない。完成予定図と標準画風を最終プロンプトへ含めて生成する。
- 構図、固定文字列、人物同一性が合格し、水彩質感だけが不足する場合に限り、背景紙と色面へ薄い水彩質感だけを加える編集を候補にする。
- 再生成や画像編集の前に、観測した問題、変更する箇所、保持する箇所、副作用の可能性をまとめて再レビューする。情報過多ならコピーと構成へ戻る。コピーを変更した場合は記事との一致、指定文字列、文字配置を再確認する。ユーザー指定を無断で別の意味へ変えない。
- 修正計画に未解決問題がある間は画像を変更しない。文字だけの問題で構図や人物を変えず、水彩だけの問題で文字や輪郭をぼかさない。
- 日本語の誤字・文字化けは対象文字だけを指定して最大2回修正する。直らなければ不採用とし、文字を消して合格にしない。文字量の見直しでも要点を残し、意味を変えない。
- その他の修正は一度に観測済みの主問題1つへ絞り、既に合格した人物同一性、構図、配色、文字を保持する。

問題を次に分類し、分類に対応する工程へ戻す。

| 分類 | 対応 |
| --- | --- |
| `message` | `thumbnail_message`の導出へ戻る |
| `copy` | 意味と事実を変えず、長さ、接続、表記だけを修正する |
| `hierarchy` | 文字の太さ・大きさ・色を絵と釣り合わせ、読む順を修正する |
| `concept` | 見本の構図へ偏った場合も含め、記事からの候補選定へ戻る |
| `composition` | 場面の分離、部品の寄せ集め、不自然な中央縮小を配置・余白から修正する |
| `style` | 画風、色、装飾を修正する |
| `render` | 焦点位置、安全余白、切り抜きを修正する |
| `accuracy` | 画像編集をせず、入力固定または事実・権利の根拠確認へ戻る |
| `tool` | 理由と再開条件を付けて `BLOCKED` とする |

同じ根本原因が2回続いた場合は微修正をやめて構造的に再設計する。固定回数だけで停止せず、意味のある改善が続く間は再確認する。構造を変えても改善が止まり、新しい判断材料もない場合に限って `BLOCKED` とする。

## 8. 生成後の必須判定

各項目を実物から評価し、`visual_review` に評価項目・観測箇所・`pass / revise / blocked`・理由を記録する。総合点で誤字、誤解、人物不一致などを相殺しない。初回と修正後の結果を区別し、自己レビューを独立評価と呼ばない。

### 内容と人物

- 記事の中心メッセージを一目で区別できる
- 対象学年と人物の正本が一致する
- 人物数、性別、行動、小物が設計どおり
- 顔、手、姿勢、持ち方に破綻がない

### 文字と安全性

- 有効な文字なし例外を除き、固定文字列が実画像内に存在し、1文字ずつ一致
- 承認見本と比べて文字だけが重くなく、主見出しと補足の強さが分かれ、絵との釣り合いがある
- 余分な文字、意味不明な記号、ロゴ、透かしがない
- 文字切れや主役への重なりがない
- 未確認の変動情報がない
- 水彩が背景紙と色面内部に限定され、日本語文字と主輪郭線がシャープ

### 差別化と実表示

- 生成後の視覚面6項目の観察と意味面の照合でも不採用条件に当たらず、見本の配置・動作を無批判に転用していない
- 既存画像と横並びにした小さいカード表示で取り違えない
- 320px、375px、390px、768px、PC幅で画像内の確定文字列を読め、重要要素が切れない。サイト側の見出しから意味を補って合格にしない
- 現行CSSによる `object-fit: cover` と焦点位置を反映した実表示を確認した

### 画像単体の意味と読む順

設計意図を合格根拠に使わず、まず画像と実際の記事カードだけを見て次を記録する。同じ担当者が行う場合は独立評価とは呼ばない。記録後に `thumbnail_message.one_glance_meaning` と比較する。

```yaml
image_only_readback:
  perceived_context: ""
  perceived_focus: ""
  perceived_takeaway: ""
  perceived_support: ""
  observed_reading_order: []
  result: pass | revise | blocked
```

- 画像単体で対象テーマと最重要メッセージを再記述できる
- 最初に読む要素が1つで、対象・中核・補足の順が意図と一致する
- 意図しない空白、衝突、重なり、装飾過多がなく、人物・教材・文字が部品の寄せ集めに見えない。全体の縮小による不自然な外周余白がない
- 必要な情報が不足して簡素に見える場合は、装飾だけを足さず不足する意味を特定する。主題と読む価値が伝わる画像に、本文へ任せた詳細を再追加する義務はない
- すべてを `pass` にできる場合だけ生成後判定を合格にする

## 9. 停止条件

- 文字密度が原因なら、再生成を繰り返す前に短い文言案を提示する。
- 回数を満たすためだけの再レビューや再生成は行わない。
- 観測済みの問題を直しても改善がなく、別の破綻を繰り返す場合は採用しない。
- ツール障害、中核メッセージに必要な根拠不足、権限、正本、ユーザー判断の不足は、理由と再開条件を付けて `BLOCKED` とする。補足事実がないだけで中核メッセージが成立する場合は `BLOCKED` にしない。
- 正本不足、比較不能、生成品質不足、実表示未確認は `BLOCKED` または未完了として明記する。推測で合格にしない。

## 10. 出力規格

- 必須比率: 16:9
- 希望生成寸法: 1536×864px。プレビューでは画像生成ツールのネイティブな16:9出力も許容する
- `FINAL_ASSET_READY`にする前に、`standalone_interactive`では保存承認後、`orchestrated_prepublication`では親の許可範囲確認後に公開用画像を1536×864pxへ正規化する
- 公開形式: WebP優先
- 目標容量: 300KB以下
- 500KB超: 原則再圧縮し、文字、輪郭、表情を再確認
- 既存ファイルは上書きしない
- `coverImage`更新、記事本文変更、公開は本スキルの対象外とする。親経由では親が一括承認の範囲内で新規記事へ`coverImage`を設定し、公開は別承認とする

## 11. スキル改訂時の生成試験

本節は改訂後の生成試験に使う。通常の記事1件ごとに全試験を実行しない。形式検査の合格は、生成品質の確認とは区別する。

- 性格の異なる3記事（教材選び・料金・困りごとの解決など）を選び、各記事を同じ入力条件で2回生成する。前回の試験結果・修正指摘を次の初回生成へ渡さない。別コンテキストを使うなど実際の隔離方法を記録し、独立実行できない場合はその制約を示す。独立した再生成と独立した評価者を混同しない。
- 開始時に記事と指定、スキル版、承認見本、キャラクターシート、比較する既存画像一覧、指定可能なモデル・設定・ツール条件を固定する。ファイルはパスとハッシュ等で同一性を確認する。生成ツールがモデルを公開しない場合はツール名・日時を記録し、モデル名を推測しない。
- 試験画像は次の試験の見本や既存画像一覧へ加えない。試験完了後に異なる記事の画像を並べて差別化を評価する。同じ記事の2回分は品質のぶれの確認に使い、必ず異なる構図を要求しない。
- 観測できた実行条件、初回結果、修正後結果、修正回数・原因を記録する。未解決の必須項目がある画像を合格に含めない。修正には通常と同じ再設計・停止規則を適用する。
- スキルを途中で変更した場合は別の版として結果を分け、異なる版の結果を同条件の反復として集計しない。
- 試験の生成物はプレビューとして扱い、記事の画像参照や承認見本へ自動反映しない。実運用では試験時の固定一覧ではなく、その時点の有効な記事画像を比較する。

完了報告は次の段階を分け、未実施は未実施と記録する。

| 段階 | 確認内容 |
| --- | --- |
| 実装・形式確認 | 参照先、旧指示の残存、内部整合、既存入出力との互換性、形式検査 |
| 生成試験 | 固定条件での実画像、初回・修正後の結果、小型表示、未達項目 |
| 好みとの適合確認 | 試験画像に対するユーザーの評価。自己評価で代替しない |

少数の試験から成功率や毎回の満足を保証しない。実装完了だけで「品質が安定した」と報告しない。試験結果とその後の運用で再現性を確認する。
