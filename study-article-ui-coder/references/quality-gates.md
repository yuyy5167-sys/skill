# 品質ゲート

## G0 入力・権限

- `article_text`とキーワードまたはタイトルがある。
- 出力先を決められる。
- ファイル書込み、画像使用、既存記事変更、公開の権限を個別に確認した。

## G1 正本・実装

対象プロジェクトがある場合、最新正本、frontmatter、共通CSS、実装済み部品を確認する。読めない場合は推測せず停止する。

## G2 読者・意図・記事型

- 主読者と記事の目的を一文で説明できる。
- 記事型を本文の情報から選んでいる。
- 維持対象を特定し、補足例の許可範囲を確定した。省略時は既定値を使い、親スキルの新項目対応を必須にしない。
- 本文にない情報で型の穴を埋めていない。

## G3 部品対応

- 各装飾部品に意味上の理由がある。
- 主結論・判断条件・重要な制約・期限・行動のうち必要な短い語句を強調し、過剰にも全体の強調抜けにもなっていない。親の強調計画がある場合は全項目が対応章の本文に反映されている。
- 枠・カード・CTAが連続しすぎない。
- リード直下に結論枠を自動追加していない。見本や記事型を部品挿入義務と解釈していない。
- 既存表の列・比較軸を保ち、短い見出しや固有名詞へ不要な強制改行を入れていない。
- 15文字を超える太字、段落全体の強調、並列でない説明の箇条書き化を内容レビューした。文字数・段落数だけでは不合格にしない。
- 未承認のURL、引用、画像、プロフィールを使っていない。
- 料金改定表を使う場合、適用時期、統一した比較条件、学年別の変更前後、月額差、年間差、公式出典、確認日がそろっている。
- 最大額の概要だけで対象全体を代表させず、全対象を確認できる学年別・コース別の行がある。

## G4 正規化・変換

1. パーサーと許可リストで危険入力を削除または文字列化する。
2. 変更内容を記録する。
3. 選択したアダプターの記法へ変換する。

## G5 機械監査

```powershell
python -X utf8 scripts/audit_article_markup.py --target standalone-html --input <file>
```

または標準入力を使う。終了コード0だけを機械監査合格とする。

このスキルで記事を検査するときは上記コマンドに`--readability-warnings`を追加する。既存の引数・`audit_document`の戻り値・`passed`・`issue_count`・`issues`・終了コードの意味は維持する。警告オプションなしのCLI出力は従来どおり。

オプション使用時だけ`warning_count`と`warnings`を追加する。空の生HTML段落と連続`br`の候補を、`severity: warning`で報告する。警告だけなら終了コード0だが、全体品質の合格を意味しない。各警告を修正するか、用途と実表示から許容できる理由を記録する。未確認の警告を残して完成にしない。

補助警告はHTMLパーサーを使用し、Markdownのコードフェンス・インラインコード・インデントコードとHTMLのpre/code等を除外する。Markdown全体の意味解析、太字の意味、CSS余白、数値保全の自動判定ではない。これらはG6・G7で別途確認する。入力の自動修正や安全性エラーの格下げは行わない。

対象Astroの正本と共通CSSで料金改定表が実装済みの場合は、次の許可済み接頭辞を明示する。

```powershell
python -X utf8 scripts/audit_article_markup.py --target astro-markdown --input <file> --allowed-class article-price-summary --allowed-class article-price-table
```

## G6 実表示

320、375、390、768、1280pxで確認する。

各幅で次を検査する。

- `scrollWidth <= clientWidth + 1`
- 表以外がviewport外へはみ出さない。
- CTA、FAQ、カード、固定要素が重ならない。
- タップ領域が基準以上である。
- 表ラッパー自身はviewport内にある。
- 表の最後の列までスクロールして読め、キーボードでもアクセスできる。AstroのMarkdown表とstandaloneのHTML構造を混同しない。
- 枠上端から最初の要素、タイトルから本文、最終要素から枠下端の実距離を確認する。親padding、隣接margin、適用CSSを併せて調べ、margin-topが0という理由だけで合格にしない。
- 短い／複数行のタイトル、本文のみ／リスト併用の枠を確認する。寸法は対象の正本・共通CSSに照合し、一般段落用の余白が漏れていないか確認する。
- 金額・単位・期間・例外が読める。小さな文字や内容の非表示で無理に収めない。
- 画像、長いタイトル、URL、英単語が崩れない。
- 強調計画の各語句が対応章の表示中の本文で太字になり、通常文字と見分けられる。コメント・コード・非表示要素・別章の同語句は数えない。Markdown記法がそのまま表示されていないことも確認し、実表示できなければ `rendered: not_checked` とする。
- コンソールエラー、壊れた画像、欠落アンカーがない。
- 料金改定表は680px以下で各金額の`data-label`が表示され、420px以下では金額項目が1列で読める。

画面上部だけでなく、見出し、表、レビューカード、内部リンクカード、FAQ、CTA、プロフィールのある位置を確認する。

## G7 完成候補レビュー

毎回、完成候補全体を次の5基準で確認する。

1. 原文と装飾の意味が一致する。
2. 対象読者の語調・判断材料になっている。
3. 長文に適切な視覚リズムがある。
4. 全幅で読みやすく操作できる。
5. 主張、数値、条件、引用、結論を変えていない。確認日・出典注記の対応を保持し、制作側の調査報告や同じ注記を追加していない。

原文と候補を照合し、固有名詞・URL・「〜」等も保つ。変更理由を報告しただけで数値変更を合格にしない。許可された補足例・導出計算は別記録にし、元の数値・単位・期間・計算式を確認する。補足未許可の新しい例、実体験に見える仮定例、比較条件の欠落があれば修正する。

一つでも未達なら `quality-refinement-loop` を使い、修正、G5監査、G6全幅再表示、G7全体確認を繰り返す。回数は固定しない。

初回から全基準を満たし、実際の修正がない場合は「ループした」と報告しない。同じ重要問題が改善せず、資料、実装、ユーザー判断が必要なら停止する。

## G8 引き渡し

- `coded_content`
- `component_map`
- `validation_report`
- `unresolved_items`
- `change_summary`
- 可能な場合はプレビュー

を一組で返す。

## 代表受け入れケース

1. 高校生向け勉強法でリンクがないとき、仮CTAを作らない。
2. 2サービス・3軸比較は、320pxで表だけ横スクロールする。
3. 承認済み引用がなければ、口コミ枠や星を作らない。
4. 長いタイトル・URL・英単語でも記事全体が横にはみ出さない。
5. Astroに未実装のレビュー枠を要求されたら`unsupported_component`。
6. 現行Astro正本外のグローバルデザインなら`design_migration_required`。
7. 危険なHTML入力は両アダプターで無害化・報告し、監査後に残存しない。
8. 内部リンク情報が不足したらカードを作らず未解決事項へ出す。
9. 固定トップボタンとCTAがどの幅でも重ならない。
10. プロフィールは承認済み時だけ表示し、Astro既存著者欄と重複しない。
11. 危険SVGを生インラインにせず監査で検出する。
12. 直接引用と要約を区別する。
13. 毎回完成候補レビューを行い、欠点があるときだけ実際の修正ループへ入る。
14. 料金変更記事では、価格帯だけで終わらず、同一支払い条件の学年別月額差・年間差と適用時期を示す。
15. 料金改定表は色だけで値上げを表さず、320pxでも学年、変更前後、月額差、年間差を判別できる。
16. 既存の講座表で列と比較軸を維持し、短い語を強制改行しない。
17. 数字枠は短い・長いタイトル、本文のみ・リスト併用の全幅表示で余白と条件を確認する。
18. 補足未許可では例を追加せず、許可時も必要な箇所だけに説明用と分かる例を入れる。
19. 別キーワードへ見本の講座名・金額・構成を流用しない。数値テストは固定データであり現在の実料金の根拠にしない。
20. 空段落・連続改行の警告、正当な単一改行・コード例の非警告、既存CLIと安全性エラーの互換性を`python -B -X utf8 scripts/test_audit_article_markup.py`で検証する。
21. 強調計画の語句が別章・コメント・コードにだけある場合は不合格。指定章にあるMarkdown太字とHTML strongは実表示まで照合する。親の計画が空なら採用せず、計画なしの単独利用では自律的に必要な強調を行う。
22. 異なる確認日の出典があってもUI化で一つの日付へ混同せず、申込期限・適用時期を保持する。
23. スキル更新時は形式検証、既存・追加テスト、代表原稿の生成と実表示を行う。未実施・部分確認を完全検証済みと報告しない。親スキル・サイト正本・共通CSS・記事・公開の変更を勝手に含めない。
